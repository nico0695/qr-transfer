## What this is

QR Transfer moves text and files between two devices by displaying a QR code (or a looping
sequence of them) on one screen and scanning it with the other's camera — no server, no network
request, no cloud storage. It has two areas: **Quick QR** (one-shot text ↔ QR) and **Large
Transfer** (text or a file, chunked into a QR animation with compression and checksum
verification). See [`../technical-overview.md`](../technical-overview.md) for the full technical
picture; this folder is the _visual_ counterpart, for handing off to a designer.

## How to read it

Start with [`flows/app-shell.md`](flows/app-shell.md) for the header, navigation and responsive
rules shared by everything, then read the three flow documents in order:

1. [`flows/quick-qr.md`](flows/quick-qr.md) — Generate QR and Scan QR
2. [`flows/large-transfer-send.md`](flows/large-transfer-send.md) — compose → settings → animated
   QR
3. [`flows/large-transfer-receive.md`](flows/large-transfer-receive.md) — scan → progress →
   complete / error

Each flow document embeds the relevant screenshots inline (desktop next to mobile, light then
dark) with the trigger for every state. [`flow-diagrams.md`](flows/flow-diagrams.md) has the same
flows as state diagrams, for the shape of the logic rather than its pixels.
[`components.md`](components.md) is a bottom-up index instead: one row per reusable UI piece
(button, card, dialog, notice…) with a cropped screenshot, for a component-library pass rather
than a screen-by-screen one.

The raw screenshots live under [`screens/`](screens/), grouped by module — browse there directly
if you just want the images.

## Naming convention

Every screenshot is `<NN>-<state-slug>.<viewport>.<theme>.png`:

- `NN` — order within its module, so a folder listed alphabetically reads top-to-bottom through
  the flow.
- `state-slug` — kebab-case, names the _state_, not the action that produced it (`empty`,
  `summary-too-large`, `error-verification-failed`, `fullscreen`).
- `viewport` — `desktop` (1280×800, DPR 1) or `mobile` (390×844, DPR 2, iPhone-13-class device).
- `theme` — `light` or `dark`.

Example: `screens/30-large-transfer-send/17-summary-too-large.desktop.light.png`.

The catalog is captured in English only. The app is also available in Spanish (`src/i18n.ts`); ask
if you need a Spanish pass on specific screens — the layout does not change, only string lengths.

**Not captured** (transient or requires real hardware, documented instead of screenshotted):

- Suspense loading fallbacks (`Loading scanner…`, `Loading Large Transfer…`) — code-split chunks
  load in well under a frame on a warm cache.
- The multi-camera picker `<select>` in both scanners — Playwright's fake-device flag was used
  single-camera throughout this pass; the picker is a plain `<select>`, described in the flow docs.
- The green "frame accepted" flash on the scan guide (`.scan-guide-hit`) — a 700 ms CSS fade,
  disabled under `prefers-reduced-motion`; described, not screenshotted.
- The `?debug=1` diagnostics overlay — intentionally unreachable without typing the query param;
  not part of the product surface a designer should touch.
- CodeMirror's Find panel and "Wrap: off" long-line scrolling — present in the code
  (`src/components/large-transfer/LargeTextEditor.tsx`) but dropped from this pass to keep the
  matrix focused; straightforward to add back with `npm run screenshots -- --only 30`.

## Known UX issues for the redesign

Observed while building this catalog — worth the designer's attention, not fixed here:

- **No persistence for theme or language.** Every reload resets to the OS's `prefers-color-scheme`
  and `navigator.language` (`src/App.tsx`). Only the transfer profile survives a reload
  (`src/lib/settingsStorage.ts`).
- **No routing.** Section, mode, direction and dialogs are all in-memory `useState`; there is no
  deep link to "Large Transfer → Receive" or a shareable URL for any state. Screenshots in this
  catalog can only be reached by the click sequence documented in each flow.
- **Mobile "Show QR" pattern** (`10-quick-qr-generate/04-qr-panel-after-show-qr`) — on mobile the
  QR only appears below the fold and needs an extra tap + scroll; on desktop it's a sidebar,
  always visible. Worth deciding if that's the right split-screen behavior or a stopgap.
- **Settings becomes a bottom sheet under 760 px** (`40-large-transfer-settings`) — consistent with
  the rest of the mobile layout, but it's the app's only modal, so it's worth a deliberate look
  rather than inheriting the desktop dialog's structure.
- **Two scan engines, two viewfinders.** The default WASM engine draws a framed guide box
  (`60-large-transfer-receive/02-scanning-framed`); the `html5-qrcode` fallback
  (`03-scanning-legacy`) has its own corner-bracket viewfinder with a different visual language.
  They're functionally equivalent but not visually unified — probably fine to leave as-is since
  the fallback is rare, but flagging it.
- **Error copy is dense but unstyled beyond a red paragraph** — every error state (camera denied,
  verification failed, incompatible sender, too-large) uses the same `.error` treatment. An
  opportunity to differentiate "user can retry" from "content problem" states visually.

## Regenerating the catalog

```bash
npm run screenshots              # full matrix, ~230 PNGs, ~6 minutes
npm run screenshots -- --list    # print module ids without capturing
npm run screenshots -- --only 30 # re-run one module (id prefix match)
```

The script (`scripts/screenshots/capture.ts`) drives a real Vite dev server with Playwright.
Camera-dependent screens use Chromium's fake-camera flag fed with synthetic `.y4m` videos built
from the app's own transfer pipeline (`scripts/screenshots/fake-camera/build-videos.ts`) — the
receiver genuinely decodes them, nothing about those screenshots is faked in the app itself. Both
the videos and the large binary fixtures are generated on the fly into
`scripts/screenshots/.generated/` (gitignored); only small, meaningful fixtures
(`scripts/screenshots/fixtures/*.md,*.json,*.txt,*.pdf,photo.png`) are committed.

**Screenshots are generated output — never hand-edit a PNG under `screens/`.** If a screen looks
wrong, fix the script or the fixture and re-run. Re-running overwrites files at the same path, so
the catalog is diffable across app changes (e.g. after a redesign lands, re-run and diff
`screens/` to see exactly what moved).
